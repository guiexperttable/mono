**Breaking Changes:** keine. `TableOptionsIf.direction` ist optional (Default `"ltr"`), `ExcelServiceIf.downloadExcel`
bekommt einen optionalen Parameter (eigene Implementierungen mit drei Parametern bleiben gültig),
`ConvenienceDomService` bekommt eine Eigenschaft. Die CSS-Umstellung auf logische Eigenschaften ist in LTR pixelgleich.

**Einzige sichtbare Änderung in LTR:** der Host bekommt `dir="ltr"` (beim `destroy()` wird der alte Wert wieder
hergestellt, wie bei den ARIA-Attributen). Auf LTR-Seiten ändert das nichts; auf einer RTL-Seite (`<html dir="rtl">`)
war die Tabelle bisher kaputt (negatives `scrollLeft`, Positionen von links) und ist jetzt eine saubere LTR-Tabelle –
wer sie gespiegelt will, setzt `direction: "rtl"` oder `"auto"`.

## 2. Entscheidungen

### 2.1 Strategie (Frage 1) → (a) Koordinaten spiegeln, zentral beim Schreiben

- (b) `transform: scaleX(-1)` + Zurückspiegeln: verworfen – Text-Auswahl, Tooltips, Cursor, Unschärfe, Maus-Koordinaten
  und Eingabefelder (Editor) wären gespiegelt bzw. falsch; jedes Overlay müsste zurückgespiegelt werden.
- (a) mit `left' = Gesamtbreite − left − width` an jeder Stelle: viele Stellen, jede braucht die Breite des Elternteils.
- **Gewählt:** alle Rechnungen bleiben unverändert („logisch“, x vom Anfang der Zeile). In RTL schreibt die zentrale
  Stelle `right` statt `left` (und `left` statt `right`). Weil **jede** Ebene (Host → Area → Zeile → Zelle) so
  positioniert wird, spiegelt sich der ganze Baum; die Breite des Elternteils braucht niemand. Der Host bekommt
  `dir="rtl"`: Scroll-Container, Text, logisches CSS und die Bidi-Spiegelung von Zeichen (`>` wird `<`) folgen von selbst.
- Scroll-Container in RTL: der Inhalt (`contentWrapperDiv`, Breite = Spaltensumme) steht rechts und läuft nach links
  über – genau der scrollbare Bereich eines RTL-Containers. Der sichtbare `contentDiv` (relativ) wird mit
  `right: <logisches scrollLeft>` mitgeschoben.
- Kosten in LTR: ein `if` je `setStyle`. Kein Pixel ändert sich (R15, Specs vergleichen Positionen und Attribute).

### 2.2 Option (Frage 2) → `tableOptions.direction?: "ltr" | "rtl" | "auto"`

```ts
export type TableDirection = "ltr" | "rtl" | "auto";   // rtl/table-direction.type.ts
const opts: TableOptionsIf = { ...new TableOptions(), direction: "rtl" };
```

- Default `"ltr"` (wie ag-Grid `enableRtl: false`). `"auto"` liest `getComputedStyle(host).direction` **vor** dem
  Setzen von `dir` (also `dir` an `<html>`, einem Vorfahren oder dem Host selbst); ist der Host noch nicht im Dokument,
  zählt das nächste `[dir]`-Attribut der Vorfahren.
- Ausgewertet **einmal beim Aufbau** (`EleScope`). Umschalten = neues Options-Objekt → die Wrapper bauen neu auf (wie bei
  jeder Option). Ein Umschalten zur Laufzeit hätte jede gecachte Zeile von `left` auf `right` umstellen müssen – kein
  Mehrwert gegenüber dem Neuaufbau, der Showcase zeigt den Umschalter so.
- API: `tableApi.getDirection(): "ltr" | "rtl"` (aufgelöst), `tableScope.isRtl()`.
- `TableOptions` (Klasse) setzt `direction` **nicht** (bleibt `undefined` = `"ltr"`): so erben verschachtelte Tabellen
  (Master/Detail `ctx.createTable()`) die Richtung der äußeren, solange sie keine eigene angeben.

### 2.3 West/East (Frage 3) → intern „west = Anfang“, Namen bleiben

- `west` = **Anfang** der Zeile (LTR links, RTL rechts), `east` = Ende. Kein Umbenennen im Code (Klassen
  `ge-table-*-west-*`, `SideIdent`, `fixedWestSeparatorBorderVisible`).
- `fixedLeftColumnCount` = Spalten am **Anfang** (RTL: rechts), `fixedRightColumnCount` = am **Ende** (RTL: links) –
  R2. Die Doku erklärt das; die Namen bleiben (Breaking Change sonst).
- Ebenso alle „logischen“ Namen der API: `ActionId` `NAVIGATE_LEFT` = rückwärts in Leserichtung, `FillDirection`
  `"right"` = vorwärts, `ensureColumnIsVisible`, `scrollToIndex`, `GeScrollEvent.scrollLeft` (≥ 0, Abstand vom Anfang),
  `TableStateIf.scroll.left` (dito), `scrollToPixel(x, y)` (x vom Anfang). Physisch bleiben nur Werte direkt aus dem
  Browser-Ereignis: `GeMouseEvent.originalEvent`, `draggingX`.

### 2.4 `scrollLeft`-Normalisierung (Frage 4) → `rtl/scroll-left.ts`

```ts
getLogicalScrollLeft(el, rtl)          // rtl ? max(0, −el.scrollLeft) : el.scrollLeft
setLogicalScrollLeft(el, x, rtl)       // el.scrollLeft = rtl ? −x : x
canScrollHorizontally(el, dx, rtl)     // innere Scroller (Mausrad-Weitergabe Master/Detail)
toLogicalX(clientX, left, width, rtl)  // Host-x vom Anfang
```

- Grundlage: CSSOM View (seit Chrome 85, Firefox, Safari): in RTL ist `scrollLeft` am Anfang 0 und wird nach links
  negativ. Das alte Chrome-Verhalten (positiv, Maximum am Anfang) wird nicht unterstützt (Chrome < 85, 2020).
- Browser-Matrix:

| Browser | Ergebnis | Wie geprüft |
|---|---|---|
| Chromium 141 (Playwright) | R1–R15 grün | Browser-Specs (`rtl/rtl.browser.spec.ts` + parametrisierte bestehende Specs) |
| Firefox | **offen (manuell)** – CSSOM-konformes negatives `scrollLeft` seit jeher, Scrollbar links | nicht im Container verfügbar; Prüfung durch Marc vor dem Release |
| Safari | **offen (manuell)** – negatives `scrollLeft` seit Safari 15 (2021); Lage der Scrollbar (macOS: Overlay) prüfen | dito |

  Risiko Safari (Abschluss-Review): bleibt die senkrechte Scrollbar eines RTL-Containers physisch **rechts** (macOS mit
  „Scrollbalken immer einblenden“ bzw. Maus; Overlay-Scrollbars sind unkritisch), liegt sie am **Anfang** des Viewports –
  zwischen fixierten Anfangsspalten und Mitte. Dann wären die Body-Zellen der Mitte um die Scrollbar-Breite (~15 px)
  gegenüber Header/Footer verschoben, Hover-Spalte, Fill-Handle und `getBodyCellAtHostPoint` ebenso (`clientLeft` ist
  dann 0, nichts gleicht aus). Kein Code auf Verdacht (nicht testbar im Container): erst manuell prüfen; falls nötig, den
  Versatz `offsetWidth − clientWidth − clientLeft` je Layout messen und in RTL auf die Mitte addieren (`TODO.md`).

### 2.5 CSS (Frage 5) → logische Eigenschaften

- `padding-left/right` → `padding-inline-start/end`, `text-align: left/right` → `start/end`, `margin` des Fill-Handles
  → `margin-block-start`/`margin-inline-start`. In LTR identisch; Anwender-CSS mit höherer Spezifität gewinnt wie bisher.
- **`ge-table-text-align-left/-right`** (Standard für Text- bzw. Zahlenspalten, `aligns.ts`, `ColumnDefGeneratorService`)
  werden dadurch in RTL gespiegelt: „left“ heißt „Anfang“. So wird eine bestehende Tabelle mit **einer** Option richtig
  herum (Text rechts, Zahlen links – wie Excel in einem RTL-Arbeitsblatt). Neu: `ge-table-text-align-start/-end` als
  eindeutige Namen. Wer Zahlen in RTL rechts haben will (R9 „oder Option“): eigene Klasse mit `text-align: right`
  (Beispiel in `instructions.md`).
- RTL-Regeln für Symbole, die **gedreht** werden (Unicode-Spiegelung allein reicht dort nicht):
  - Baum-Pfeil aufgeklappt: Standard-Icon `rotate(90deg)` würde den gespiegelten `<` nach **oben** drehen →
    `.ge-table[dir="rtl"] .gt-table-tree-arrow-expanded` dreht um −90° (mit `!important`, weil der Stil inline steht;
    nur die Klasse des Standard-Icons).
  - Master/Detail-Dreieck (CSS-Rahmen): Rahmen gespiegelt, aufgeklappt −90°.
- Latein mit Satzzeichen in RTL ("Rossi S.p.A." erscheint nach Unicode-Bidi als ".Rossi S.p.A" – korrekt nach dem
  Algorithmus, aber unschön): **opt-in** Klasse `ge-table-text-plaintext` (Label `unicode-bidi: plaintext`, Zelle
  physisch am Tabellenanfang ausgerichtet – `start` würde bei `plaintext` je Text aufgelöst und Latein nach links
  schieben). Kein Default, weil es die Ausrichtung je Zelle festlegt (Spec-Verhalten wie native RTL-Tabellen bleibt).
- Zahlen/Datum (Frage 7): **kein** `direction: ltr` auf Zellen. Der Bidi-Algorithmus stellt Ziffernfolgen ohnehin von
  links nach rechts dar (R12: „١٢٣ Riad 2026“ bleibt lesbar). Ein erzwungenes `ltr` würde Zahlen mit arabischem
  Text daneben (Einheiten, Währung) zerreißen.

### 2.6 Tastatur (Frage 6)

- Im Tastenkürzel werden `left`/`right` getauscht, bevor das Mapping gesucht wird: → = `NAVIGATE_LEFT` (rückwärts, also
  zur rechts liegenden Spalte), ← = vorwärts (R8). macOS ⌘← / ⌘→ folgen automatisch (⌘← = Zeilenende = links).
  Pos1/Ende, Strg+Pos1/Ende sind ohnehin logisch.
- Eigene `shortcutActionIdMapping`s sind damit in LTR-Begriffen geschrieben („left“ = rückwärts). Dokumentiert.
- Baum-Tasten (001): Auf/Zu über Enter, keine Pfeiltasten → nichts zu tun. Row Drag (Strg+Alt+↑/↓) senkrecht → nichts.
  Fill (Strg+R = `FILL_RIGHT`) füllt in Leserichtung vorwärts (wie Excel RTL).

### 2.7 Excel (Frage 8) → ja, `rightToLeft`

```ts
export interface ExcelExportOptionsIf { rightToLeft?: boolean }       // service/excel-export-options.if.ts
await new ExcelService().downloadExcel(matrix, "orders.xlsx", "", { rightToLeft: true });
```

`TableApi.downloadExcel()` setzt es automatisch für RTL-Tabellen (Spalte A steht dann in Excel rechts – wie in der
Tabelle). `createExcelBlob(matrix, author, options)` ebenso.

### 2.8 Was sich automatisch ergibt (R13)

| Feature | Ergebnis in RTL |
|---|---|
| Header-Gruppen, Col-/Rowspan (R10) | `drawBigCell` rechnet logisch → gespiegelt |
| Zeilennummern (004) | erste fixierte Spalte = ganz rechts, Text am Ende (zur Datenspalte hin) |
| Overlay (002) | über die zentrale Stelle, zentriert |
| Row Drag (009) | Griff `inset-inline-start` (war schon logisch), Marke über die volle Breite, Geisterbild links vom Zeiger |
| Fill-Handle (010) | Ecke unten am **Ende** (links) des Bereichs; Ziel über `toLogicalX`; Auto-Scroll in Leserichtung |
| Master/Detail (011) | Ebene gespiegelt, Dreieck zeigt nach links, verschachtelte Tabellen erben RTL |
| Row Grouping/Pivot (006/007) | CSS schon `start`/`end`; Gruppenspalte fixiert am Anfang (rechts) |
| Sortier-Icon | am Ende der Kopfzelle (links), Platz über `padding-inline-end` |
| Hover-Spalte, Fokusrahmen, Auswahl, Drop-Zone | logisch → gespiegelt |
| Spalten-Drag (R5) | Ziel aus dem DOM, Geisterbild unter dem Zeiger (`clientXToHostX`) |

Nebenbei gefunden: das Spalten-Geisterbild in **LTR** steht um den Abstand des Hosts vom linken Fensterrand versetzt
(`clientX − width/2` ohne Host-Versatz). In RTL wird richtig gerechnet; LTR bleibt wegen R15 (pixelgleich) unverändert
→ `TODO.md`.

## 6. Abschluss-Review (separater Agent) und Korrekturen

Ein Agent, der den Code nicht geschrieben hat, hat den Diff gegen `1725d90` gelesen (Schwerpunkte aus dem Prompt:
LTR-Pixelgleichheit, `scrollLeft`-Randfälle, Maus in RTL, Browser-Unterschiede, Aussagekraft der Tests). Ergebnis: die
Strategie trägt; alle verbliebenen `scrollLeft`/`clientX`/`style.left`-Stellen sind entweder logisch, bewusst physisch
(Mausrad, `draggingX`) oder laufen über `ConvenienceDomService`. Funde und was daraus wurde:

| # | Fund | Art | Ergebnis |
|---|---|---|---|
| 1 | Optionen verschachtelter Tabellen wurden **immer** kopiert (auch LTR) – spätere Änderungen am Options-Objekt der App (z. B. `externalFilterFunction`) kamen nicht an | Bug | behoben: Objekt unverändert; nur RTL ohne eigene Richtung ein Objekt mit dem Original als Prototyp (`TableScope.nestedTableOptions`); Spec |
| 2 | Safari: Scrollbar rechts in RTL verschiebt die Mitte | Risiko | dokumentiert (§ 2.4), manuelle Prüfung in `TODO.md` |
| 3 | RTL-CSS (`.ge-table[dir="rtl"] .x`) wirkt auch in einer **LTR-Tabelle innerhalb** einer RTL-Tabelle | Risiko | behoben: `:not(.ge-table[dir="rtl"] .ge-table[dir="ltr"] .x)` (Selectors 4, Chrome 88/Firefox 84/Safari 9); Spec |
| 4 | CRUD-Dialoge hängen an `document.body` – ohne `dir` der Tabelle | Risiko | behoben: `CrudObjectView/Edit.direction`, von der Fabrik gesetzt; Spec |
| 5 | Editor-Padding physisch (`padding:0 0 0 8px`) | Nit | behoben: `padding-inline-start` (LTR gleich) |
| 6 | `canScrollHorizontally` änderte die LTR-Grenzen der Mausrad-Weitergabe minimal | Nit | behoben: LTR wie vorher, Toleranz nur RTL |
| 7 | Pfeil-Test hätte auch ohne RTL-Regel bestanden | Nit | behoben: prüft die Drehmatrix (−90°) |
| 8 | `Math.abs(scrollLeft)` in den parametrisierten Specs verdeckt Vorzeichenfehler | Nit | behoben: in RTL wird `scrollLeft ≤ 0` geprüft; Positionen auf dem Bildschirm prüft `rtl.browser.spec.ts` |
